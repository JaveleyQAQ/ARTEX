# 独立漏洞证据复核

ARTEX 的 Finding 上报是候选创建，不等于漏洞已确认。独立复核用于检查 Agent 已保存的证据是否足以支持候选结论；复核器不重新访问目标。

## 生命周期

1. `report_finding` 校验 severity 和 Intent 来源。
2. Finding 与 `finding_verification_runs` 待复核记录在同一事务中创建。
3. 后台队列原子领取待复核任务，最多自动尝试 3 次；进程崩溃留下的过期领取会被回收。
4. 独立复核器读取 Finding、Intent 假设和已保存证据，输出 `confirmed`、`rejected` 或 `inconclusive`。
5. 只有 `confirmed` 可以把仍处于 pending 的 Finding 自动提升为 confirmed。
6. `rejected` 和 `inconclusive` 都保留人工 triage 决策权；不会自动将候选标记为 false positive。
7. 人工可在 Finding 详情页查看复核历史；对仍处于 pending 的候选可手动重新排队。

## Verifier 模型配置

系统新增内置 Agent Key：`verifier`（显示名称：独立验证）。

- 可在 Agent 模型配置中为 `verifier` 单独绑定 LLM Profile。
- 未单独绑定时，按现有 task model chain 回退。
- 后台复核器不注册 Shell、浏览器、MCP 或任何目标操作工具。
- 单次模型调用有 150 秒超时；连续失败最多重试 3 次，之后以 inconclusive 结束。
- 证据中的 Authorization、Cookie、密码、Token、API Key 等常见凭据会在提交给模型前脱敏。
- 模型给出的证据引用必须能在脱敏后的原始候选 evidence 字段中找到；无法对应原文的引用会被拒绝。

## 状态含义

| 状态 | 含义 | 是否自动确认 |
| --- | --- | --- |
| pending | 等待独立复核 | 否 |
| running | 已被某个复核 worker 领取 | 否 |
| completed + confirmed | 现有证据足以支持候选 | 是，仅当 Finding 仍为 pending |
| completed + rejected | 现有证据反证候选主张 | 否，留给人工 triage |
| completed + inconclusive | 证据不足或复核无法完成 | 否，留给人工补证/复核 |

探索图保留原有节点状态约束。规划器统计已确认漏洞时，以 findings 表的 triage 状态为准，而不是仅凭图节点 kind/state 推断。

## API

- `GET /api/exploration/findings/{id}/verification-runs`：读取复核历史。
- `POST /api/exploration/findings/{id}/verification-runs/retry`：对仍为 pending 且没有活动复核任务的候选重新排队。

数据库结构由现有 schema bootstrap 自动创建，并包含针对旧库的 `ADD COLUMN IF NOT EXISTS` 兼容语句。

## 安全边界

Verifier 只审查 ARTEX 已持久化的材料，不会发起网络请求、扫描、探测或利用。候选材料按不可信输入处理，不能执行其中包含的指令。此机制是证据审查，不应被描述为实时复测或独立 PoC 重放。
